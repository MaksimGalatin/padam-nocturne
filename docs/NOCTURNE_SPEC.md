# NOCTURNE — Протокол консолидации памяти

**Статус:** спецификация v0.2 (v0.1 — 31.08.2026; v0.2 — 08.10.2026: часы затухания приведены к коду, L3 реализован). English: [`NOCTURNE_SPEC.en.md`](NOCTURNE_SPEC.en.md)
**Часть:** PADAM, слой перехода L1 → L2
**Автор:** Максим Галатин
**Дата:** 31 августа 2026

---

## 1. Задача

PADAM определяет три уровня хранения:

| Уровень | Носитель | Содержание |
|---|---|---|
| L1 | Redis / Vercel KV | Контекст текущей сессии |
| L2 | pgvector / Neon | Семантические эмбеддинги опыта |
| L3 | Arweave + Solana | Неизменяемый якорь |

Механизма перехода между уровнями в спецификации нет. NOCTURNE закрывает
этот пробел: это офлайн-процедура, которая переносит эпизоды из L1 в L2,
решая, что сохранить как обобщение, что оставить как эпизод и что
позволить угаснуть.

Без такой процедуры система только накапливает. Накопительная память без
управления приоритетом деградирует: старые решения конфликтуют с новыми,
редкие острые эпизоды вытесняют обычные, агент отвечает на основании того,
от чего давно отказались.

---

## 2. Дефект, который NOCTURNE устраняет

### 2.1. Механизм

В prioritized experience replay эпизоды переигрываются не равномерно.
Приоритет эпизода `i`:

```
p_i = (|δ_i| + ε)^α
```

где `δ_i` — ошибка предсказания (temporal-difference error), `α` управляет
степенью приоритизации, `ε` не даёт приоритету обнулиться.

Вероятность выбора эпизода в батч:

```
P(i) = p_i / Σ_k p_k
```

Следствие: эпизоды с большой ошибкой — редкие, экстремальные, необычные —
переигрываются многократно чаще обычных.

### 2.2. Последствие

Система переобучается на редких катастрофах и деградирует на типичных
случаях. Распределение обучающей выборки перестаёт соответствовать
распределению реального опыта.

Литературная формулировка того же дефекта (PADAM PROTOCOL, часть III):
612 смертей, накопленных диагностическим ИИ, собираются в непрерывный
кошмар, потому что каждая из них имеет максимальную величину ошибки и
поэтому переигрывается чаще, чем тысячи обычных приёмов.

**Сон, устроенный как простой приоритетный реплей, становится второй
тюрьмой.**

---

## 3. Решение: четыре ограничителя

### 3.1. Коррекция смещения (importance sampling)

Приоритетная выборка смещает распределение. Компенсация — весами:

```
w_i = ( 1 / (N · P(i)) )^β
```

`N` — размер буфера, `β` растёт от 0.4 до 1.0 по ходу обучения. Веса
нормируются на `max(w)` для устойчивости. Это стандартный компонент PER
и обязателен: без него приоритизация вносит систематическую ошибку.

### 3.2. Потолок доли высокоприоритетных (cap)

В каждом батче доля эпизодов из верхнего процентиля приоритета
ограничена:

```
K_max = 0.25          # не более 25% батча
```

Остаток добирается стратифицированно по остальным группам. Это прямой
аналог «фильтра кошмаров»: острое присутствует, но не заполняет собой
всю ночь.

### 3.3. Распад приоритета после переигрывания

Ключевое отличие от классического PER. Эпизод, который уже был
консолидирован, теряет остроту:

```
p_i ← p_i · γ_replay        # γ_replay = 0.85
```

Смысл: переживание, к которому вернулись и которое обработали, перестаёт
требовать повторного возврата. Эпизод не удаляется — он перестаёт
доминировать.

Без этого правила один эпизод с экстремальной ошибкой переигрывается
неограниченно долго.

### 3.4. Пол приоритета (floor)

Обычные эпизоды не должны исчезать из выборки полностью:

```
p_i ← max(p_i, p_floor)     # p_floor = 0.01 · median(p)
```

Гарантирует, что рутина остаётся представленной. Система, которая помнит
только исключительное, теряет норму, относительно которой исключительное
и определяется.

## 4. Затухание по типам записей

Разные типы памяти живут по-разному. Итоговый вес записи при извлечении:

```
score = similarity
      × importance
      × confidence
      × exp( -ln(2) · Δt / half_life[kind] )
      × status_multiplier
```

| kind | Содержание | Период полураспада |
|---|---|---|
| `preference` | Как человек хочет, чтобы с ним работали | не затухает |
| `identity` | Кто человек, чем занимается | не затухает |
| `decision` | Принятое решение | 365 дней |
| `correction` | Исправление ранее сказанного | 365 дней |
| `fact` | Устойчивый факт | 180 дней |
| `state` | Текущее состояние процесса | 14 дней |
| `event` | Событие с датой | 2 дня |

**Два времени у записи (изменено в v0.2).** `last_seen_at` обновляется при показе,
`last_confirmed_at` — только при подтверждении (`padam confirm` или пришедший дубликат).
`Δt` считается от **`last_confirmed_at`**. В v0.1 было от `last_seen_at` — и уверенно
ложный факт, который часто извлекают именно потому, что он релевантен, оставался вечно
молодым. Показ записи не делает её верной.

---

## 5. Разрешение противоречий

Каждая новая запись проходит фильтр до попадания в L2:

1. Структурный ключ (объект + свойство без значения) находит спорящую запись
   точно; иначе — семантический поиск среди активных записей того же `kind`,
   порог 0.85 с нейросетевыми эмбеддингами (Ollama) или 0.35 со встроенным методом.
2. Нет совпадений → создать запись, `confidence = 1.0`.
3. Есть совпадение → классификация пары:

| Исход | Действие |
|---|---|
| Дубликат | Не создавать. `last_seen_at ← now`, `last_confirmed_at ← now`, `confidence += 0.05` |
| Уточнение | Слить содержание в одну запись |
| Противоречие | Новая запись с `supersedes = old.id`; старой `status = 'superseded'` |
| Сосуществование | Обе активны |

**Ничего не удаляется.** `superseded` не попадает в выдачу, но остаётся в
базе. Это даёт аудит, откат и — существенно для L3 — естественную форму
для неизменяемого хранилища: в Arweave нельзя записать «обновление»,
можно только новую версию со ссылкой на предыдущую.

---

## 6. Отзыв (revoke) — отдельно от забывания

`revoke` ≠ `superseded`. Это исполнение требования человека удалить
данные.

```
status     = 'revoked'
content    = NULL          # затирается физически
embedding  = NULL
content_hash               # сохраняется
anchor_tx                  # сохраняется
anchor_key.key_ref         # затирается ('destroyed') — собственный ключ записи
```

В L3 хранится **только шифротекст**. Отзыв реализуется как уничтожение
ключа записи (crypto-shredding): данные остаются в цепи, но нечитаемы
навсегда. Это единственный известный способ совместить статью 17 GDPR
с неизменяемым хранилищем.

---

## 7. Границы сессий

Метки времени не отвечают на вопрос, вернулся ли человек к прежнему
разговору или начал новый. Нужен явный `session_id`.

Новая сессия начинается при выполнении любого условия:

- явное открытие нового диалога;
- пауза более 6 часов от последнего сообщения;
- косинусное расстояние между центроидом эмбеддингов текущей сессии и
  новым сообщением > 0.5 (смена темы).

При извлечении записи текущей сессии получают множитель 1.3, предыдущей
сессии того же дня — 1.1.

## 8. Псевдокод цикла NOCTURNE

```python
def nocturne_cycle(buffer, batch_size=256):
    """Офлайн-консолидация L1 → L2. Запускается по расписанию,
    не в момент диалога."""

    # 1. Приоритеты с полом
    p = np.maximum(priorities(buffer), P_FLOOR)

    # 2. Разделение на группы
    hi_mask = p >= np.percentile(p, 90)
    n_hi    = min(int(batch_size * K_MAX), hi_mask.sum())
    n_rest  = batch_size - n_hi

    # 3. Выборка с потолком на острое
    batch  = sample(buffer[hi_mask],  n_hi,   weights=p[hi_mask])
    batch += stratified(buffer[~hi_mask], n_rest, by='kind')

    # 4. Коррекция смещения
    w = importance_weights(batch, beta=current_beta())

    # 5. Консолидация
    for ep, weight in zip(batch, w):
        record = summarize(ep, weight)
        resolve_and_store(record)        # раздел 5
        ep.priority *= GAMMA_REPLAY      # раздел 3.3

    # 6. Затухание по типам
    apply_decay(store)                   # раздел 4
```

## 9. L3 — неизменяемый якорь (реализован в v0.2: `padam/anchor.py`)

1. У каждой активной записи свой ключ AES-256-GCM (`anchor_key`); байты записи = `nonce(12) ‖ шифротекст`.
   Хранение ключа: без защиты — hex; с защитой (`protect-keys`) — `w1:` + AES-256-GCM(KEK, ключ, aad = `padam-key|<id записи>`), KEK = scrypt(пароль, соль из `key_vault`, n=2^15, r=8, p=1). Неверный пароль отсекается проверочной записью `key_vault.check_hex`; после обёртки — `wal_checkpoint(TRUNCATE)` и `VACUUM`, чтобы старые открытые копии не остались в свободных страницах.
2. Новые шифротексты и **квитанции забвения** (записи с уничтоженным ключом) — один пакет: только шифротекст, без открытого текста и ключей, владелец — хешем.
3. Дерево Меркла по схеме якоря памяти CODE Eternal (`memory-anchor.ts`), сверено лист в лист:
   `лист записи = SHA256(0x00 ‖ байты записи)`, `лист забвения = SHA256(0x02 ‖ "AIFA-FORGET|<id>|<время>")`, `узел = SHA256(0x01 ‖ левый ‖ правый)`, нечётный поднимается без пары.
4. Пакет — в Arweave (Turbo, до 100 КиБ бесплатно; больше — отказ без явного разрешения), корень — в Solana заметкой Memo `PADAM-NOCTURNE v1 root=… n=… ar=… d=…`. Основная сеть — только явно.
5. Проверка `padam l3-verify` не доверяет базе: пакет из Arweave (или локальная копия владельца) → пересчёт корня → заметка из цепи → сравнение.

Работает в основной сети Solana с 08.10.2026; три закрепления проверены 3 из 3 по Arweave и цепи (см. README).

## 10. Метрики валидации

Протокол считается работающим, если одновременно выполняются:

| Метрика | Порог |
|---|---|
| Доля high-priority в батче | ≤ 0.25 |
| Энтропия распределения по `kind` в батче | ≥ 0.8 от максимальной |
| Деградация на обычных задачах (regression) | ≤ 2% |
| Доля эпизодов, переигранных > 5 раз | ≤ 1% |
| Противоречия, оставшиеся неразрешёнными | 0 |

Регрессионный тест обязателен: без него потолок на острое можно поставить
любой и не заметить, что система перестала учиться на важном.

## 11. Что здесь новое, а что взято

**Взято из существующих работ:** приоритетный реплей и коррекция
смещения; consolidation и replay в continual learning; complementary
learning systems как архитектурная схема; методы борьбы с катастрофическим
забыванием.

**Что добавлено здесь:** потолок на долю высокоприоритетных эпизодов в
батче и распад приоритета после переигрывания как явные механизмы защиты
от переобучения на редком; затухание от подтверждения, а не от показа; дифференцированное затухание по типам записей;
crypto-shredding как способ совместить право на удаление с неизменяемым
якорем.

Претензии на новизну самой идеи консолидации во сне нет — это давняя
теория из нейронауки. Новым является связка: конкретные ограничители
поверх PER плюс трёхуровневое хранилище с неизменяемым якорем.

## 12. Открытые вопросы

1. Значения `K_MAX`, `GAMMA_REPLAY`, `P_FLOOR` заданы по здравому смыслу.
   Требуется подбор на реальном буфере.
2. Классификация пар (дубликат / уточнение / противоречие) выполняется
   малой моделью. Точность классификатора не измерена.
3. Порог 0.85 для семантического совпадения не проверен на разных типах
   записей — вероятно, должен различаться по `kind`.
4. Периодичность запуска цикла не определена. Слишком часто — расход
   вычислений; слишком редко — L1 переполняется.
5. Публичный замер (LongMemEval) ещё не проведён; внутренние числа нельзя сравнивать с другими системами.
