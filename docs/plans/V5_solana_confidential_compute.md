## 1. Как связать «память нельзя подменить» (L3 PADAM) и «вычисление нельзя подсмотреть» (TEE)

У нас и у Solana Confidential Compute **разные, взаимно дополняющие уровни гарантий**:
- **PADAM L3 (`padam/anchor.py`, mainnet с 08.10.2026):** доказывает математикой (хешами SHA-256 и деревом Меркла `0x00`/`0x01`/`0x02`), что *память не подменили задним числом*, причём сам шифротекст в Arweave зашифрован по-записно AES-256-GCM с правом на забвение через уничтожение ключа в `anchor_key` и публикацией листа забвения `AIFA-FORGET|<id>|<ts>`. Но если память обрабатывается на обычном сервере в открытом ОЗУ, пользователь вынужден верить владельцу сервера на слово, что память не подсмотрена во время поиска/вывода.
- **Solana Confidential Compute (devnet beta):** доказывает аппаратной подписью процессора (AMD SEV-SNP, Intel TDX; в разработке NVIDIA GPU), что программа работает внутри «запечатанного» анклава TEE, чей публичный ключ подписи рождается внутри анклава, не покидает его и привязывается on-chain-программой верификации к отпечатку одобренного кода и свежему слоту Solana. Проверка этого доказательства другими программами/агентами в Solana укладывается примерно в `<= 1 500 compute units`.

**Архитектура связки (без подмены L3):**
1. **Запуск доверенного агента / воркера памяти внутри TEE:** образ `padam`-агента (или будущего облачного обработчика AIfa Memory) собирается воспроизводимо; отпечаток кода вносится в одобренный список.
2. **Аппаратная регистрация ключа в Solana:** при старте анклав генерирует пару ключей Ed25519 в запечатанной памяти и публикует аппаратное доказательство (attestation report) через программу верификатора Confidential Compute.
3. **Связывание с L3 PADAM и облаком AIfa Memory:**
   - Агент подписывает исходящие записи/пакеты своим аппаратно-аттестованным ключом анклава.
   - Облако AIfa Memory (или принимающий узел) перед приёмом записи от удалённого агента проверяет в Solana наличие свежей, не просроченной записи верификатора для этого ключа и отпечатка кода — защита от поддельного агента.
   - Сама память продолжает закрепляться по схеме **L3 PADAM**: шифротекст -> Arweave, корень Меркла -> Solana Memo (`padam/anchor.py`), ключи записей -> внутри TEE или у владельца (с сохранением квитанции `forget_receipt`).
   - Итоговое свойство: **память нельзя подменить задним числом (L3) И нельзя подсмотреть в ОЗУ сервера при обработке (TEE)**.

## 2. Можно ли проверить их запись в devnet бесплатно, без своего анклава

**Да, чтение и верификация на стороне проверяющего стоят $0:**
- Проверка записи верификатора в сети Solana `devnet` сводится к обычному RPC-чтению состояния аккаунта/PDA (`getAccountInfo` / `getTransaction` через публичный `https://api.devnet.solana.com`) или симуляции инструкции <= 1 500 CU. Свой TEE-сервер и платные ключи для **проверки уже существующего доказательства** не нужны.
- А вот **создание собственной аппаратной аттестации** (чтобы наш код реально крутился в TEE и сам подавал доказательства в devnet) требует запуска ВМ на поддерживаемом облачном железе AMD SEV-SNP / Intel TDX (либо AWS Nitro, если поддерживается их SDK) — это уже платно (см. ниже).
- **Важный пробел на сегодня (честная оговорка):** по состоянию на 14.11.2026 точный адрес devnet-программы и открытый GitHub-репозиторий с исходниками верификатора в кэшированных страницах и нашем поиске не зафиксированы (анонс и документация свежие, аудит не пройден). Поэтому первым делом при старте работ (стоимость $0) нужно найти официальный devnet Program ID и разобрать бинарную/Anchor-схему PDA верификатора по публичному `devnet` без запуска ВМ.

## 3. Что стоит платное железо и сколько нужно работы

1. **Актуальная стоимость TEE-железа (на момент оценки):**
   - **Google Cloud Confidential VM (N2D с AMD SEV-SNP):** помимо стандартной почасовой ставки выбранного N2D-инстанса Compute Engine, берётся отдельная надбавка за режим Confidential Computing:
     * **vCPU:** `$0.0027502 / vCPU-час` (on-demand) или `$0.000436 / vCPU-час` (Spot);
     * **RAM:** `$0.0003686 / GiB-час` (on-demand) или `$0.0000584 / GiB-час` (Spot).
     * То есть сама «запечатанность» для машины 2 vCPU + 8 GiB RAM добавляет менее ~$6.20/мес поверх обычной цены ВМ N2D (итоговая цена вместе с базовым N2D зависит от региона — ориентировочно ~$45–75/мес при работе 24/7, либо копейки за короткий тестовый прогон в несколько часов).
   - **AWS Nitro Enclaves:** `$0` дополнительной наценки за сам анклав — оплачивается только базовый EC2-инстанс (при условии поддержки Nitro Enclaves для выбранного семейства, без прямого сетевого интерфейса внутрь анклава).
   - При наличии бесплатных trial/startup-кредитов облака опытный прогон занимает единицы долларов, но без отдельной санкции Архитектора никакое облачное железо не запускается.

2. **Объём работ:**

| Шаг | Содержание работ | Затраты на инфраструктуру | Срок |
|---|---|---|---|
| 1 | Найти официальный репозиторий / devnet Program ID, написать read-only CLI-проверщик аттестации по `devnet` JSON-RPC | $0 | 1–2 дня |
| 2 | Связать проверку подписи TEE-агента со входом `/write` облака AIfa Memory (режим devnet-эксперимента) | $0 (при моках/существующих devnet-записях) | 2–3 дня |
| 3 | Воспроизводимый Docker-образ воркера + стенд в Google Confidential VM (N2D AMD SEV-SNP) для генерации живого доказательства | Платное облачное железо (по санкции) | 3–5 дней |
| 4 | Переход в `mainnet` | **Только после независимого аудита Solana Foundation и выхода программы из беты** | отложено |
