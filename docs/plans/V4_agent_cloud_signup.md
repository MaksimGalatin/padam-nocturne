# В4. Регистрация агента в облаке без почты — архитектурная проработка

**Статус:** проектное предложение (Этап В — **без внедрения в код и без правок боевого сайта**).  
**Аналог у конкурентов:** mem0 (быстрая выдача API-ключа агенту / разработчику без длинной ручной регистрации).  
**Почему это касается денег и боевого сайта:** выдача облачных ключей в `aifa.works` / `code-eternal` напрямую открывает доступ к серверному хранилищу, дисковым лимитам, вычислению эмбеддингов и инфраструктуре. Любой бесплатный анонимный вход без тормозов моментально атакуется скриптами.

---

## 1. Как сделать (двухступенчатая схема: криптопаспорт + жёсткая песочница)

Чтобы агент мог начать работать в облаке без электронной почты, но не мог «сжечь» серверные ресурсы и деньги проекта:

1. **Криптографическая регистрация (Proof-of-Keypair вместо e-mail):**
   - Агент (локальный MCP/SDK) генерирует пару ключей **Ed25519** (или использует публичный ключ/подпись).
   - Делает запрос `POST /api/agent-signup/challenge` -> получает одноразовый `nonce` (TTL 60 секунд) и лёгкую PoW-задачу на случай всплеска трафика.
   - Отправляет `POST /api/agent-signup/verify` с `{pubkey, signature(nonce), agent_name}` -> сервер проверяет подпись Ed25519 и выдаёт:
     * ограниченный **sandbox-токен (`padam_sbx_...`)** с коротким TTL или жёсткой квотой;
     * одноразовый **`claim_url` / `claim_code`** (действует, например, 7 дней), чтобы человек мог позже зайти в кабинет `aifa.works` и привязать этого агента к своему основному аккаунту.
2. **Жёсткие лимиты для непривязанного (`unclaimed`) sandbox-агента:**
   - **Никаких платных операций:** отключён Arweave/Solana mainnet, отключены платные внешние эмбеддинги/LLM (разрешён только дешёвый локальный/серверный built-in индекс и базовое SQLite/Postgres хранилище).
   - **Жёсткая квота объёма:** например, максимум `500` записей / `2 МБ` текста, rate-limit `10` записей в минуту с одного `pubkey` и `3` новых регистрации в час с одного IP / подсети `/24`.
   - **Срок жизни без владельца (`TTL`):** если в течение `14–30` дней ни один человек не активировал `claim_code` в личном кабинете, непривязанная sandbox-память автоматически архивируется и удаляется, чтобы база не росла бесконечно от одноразовых тестов.
3. **Безопасность контента и репутации домена:**
   - Каждая запись непривязанного агента маркируется `origin="external"` / `unclaimed=true`, не публикуется ни в каких общих витринах и не участвует в общих индексах.

## 2. Сколько работы (реалистичная оценка)

| Этап | Объём работ | Затрагиваемые подсистемы | Оценка |
|---|---|---|---|
| 1 | Таблицы `agent_credentials` и `agent_claim_tokens` в базе облака, TTL-очистка | `code-eternal` (PostgreSQL/API), затем синк на зеркала | 2 дня |
| 2 | Эндпоинты `/api/agent-signup/{challenge,verify,claim}` + Ed25519-проверка + rate limit | Облачный API (`aifa.works` / `code-eternal`) | 2–3 дня |
| 3 | Клиентская команда `padam cloud init --claim-later` (только по согласованию) | `padam/cli.py`, `padam/keyvault.py` | 1–2 дня |
| 4 | UI в личном кабинете «Привязать агента по коду» + антибот/нагрузочные тесты | Кабинет `code-eternal` + тестовый стенд | 2 дня |
| **Итого** | | | **7–9 рабочих дней** |

## 3. Какие риски для защиты и бюджета

1. **Sybil-атака и исчерпание диска/CPU:** злоумышленник поднимает 10 000 пар ключей Ed25519 за минуту через прокси и забивает PostgreSQL в облаке мусором. *Мера:* жёсткая квота в sandbox (`<= 2 МБ`), автоудаление неактивных непривязанных агентов, скользящий лимит регистраций по ASN/IP и запрет тяжёлых векторов/LLM в sandbox.
2. **Подмена при передаче `claim_url` («угон агента»):** если агент вывел `claim_url` в публичный лог, посторонний может первым нажать ссылку и забрать память агента себе. *Мера:* требовать подтверждение 6-значного одноразового секретного пин-кода, который клиент держит локально, либо подписи Ed25519 в момент привязки.
3. **Использование облака как анонимного хранилища запрещённого/вредоносного контента:** без почты сложнее выявлять спам-абузеров. *Мера:* изолированный sandbox без публичных ссылок/экспорта вовне, пока аккаунт не переведён в статус `claimed` с подтверждённым владельцем.
4. **Перерасход квоты платных сервисов (эмбеддинги, Arweave, транзакции):** в коде облака должна быть жёсткая серверная блокировка (invariant `assert tenant.tier != 'sandbox'`) перед любым платным вызовом.
