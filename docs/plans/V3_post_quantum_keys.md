# В3. Постквантовый обмен ключами для синхронизации устройств — архитектурная проработка

**Статус:** проектное предложение (Этап В — **без внедрения в код**).  
**Аналог у конкурентов:** SAIHM (постквантовая защита канала/ключей).  
**База PADAM сегодня:** шифрование записей для L3 выполняется симметричным AES-256-GCM с индивидуальными ключами в `anchor_key` (`padam/anchor.py`), обёртка ключей паролем — `scrypt` (`n=2**15, r=8, p=1`, префикс `w1:`, `padam/keyvault.py`), аутентификация записей `identity`/`preference` — HMAC-SHA256 (`padam/integrity.py`). Механизма прямой синхронизации зашифрованных баз между двумя устройствами владельца пока нет.

---

## 1. Как сделать (гибридный обмен ключами поверх X-Wing)

Использовать чистую новую постквантовую схему без классической пары опасно: если в математике нового алгоритма найдут слабость, защита рухнет полностью. Использовать только X25519 тоже рискованно из-за атаки «перехватывай шифротекст синхронизации сегодня — расшифруй квантовым компьютером завтра». Поэтому целевой вариант — **гибридный KEM стандарта X-Wing (`X25519 + ML-KEM-768` / NIST FIPS 203)** со строгим комбинатором на SHA3-256 (`draft-connolly-cfrg-xwing-kem`), либо стандартный гибридный HPKE `MLKEM768X25519` в `cryptography` 48+:

1. **Идентификация и спаривание устройств (Out-of-band ТОП-уровень доверия):**
   - Каждое устройство генерирует долгосрочную пару подписи **Ed25519** (идентификатор устройства `device_id`) и гибридную пару KEM **X-Wing** (`pk_xwing`, `sk_xwing`, где часть ML-KEM-768 занимает `1 184` байта публичного ключа + `32` байта X25519).
   - Секретный ключ `sk_xwing` и приватный ключ устройства никогда не уходят с устройства и шифруются на диске через существующий `keyvault.py` (`w1:` AES-256-GCM от `PADAM_KEY_PASSPHRASE`).
   - При первом спаривании двух устройств (например, ноутбук и телефон/второй ПК) устройства обмениваются публичными ключами по QR-коду или короткому проверочному коду (SAS-сверка отпечатка `SHA-256(pk_A || pk_B)` глазами человека — защита от MITM).
2. **Сеансовый транспортный ключ синхронизации (Ephemeral Forward Secrecy):**
   - При каждой сессии синхронизации инициатор вызывает `encapsulate(peer_pk_xwing)` -> получает 32-байтный общий секрет `ss_pq` и гибридный шифротекст (~`1 120` байт: `1 088` байт ML-KEM-768 + `32` байта эфемерного X25519).
   - Пропускает `ss_pq` вместе с транскриптом сессии (`device_id_A`, `device_id_B`, `nonce_session`, отпечаток базы) через HKDF-SHA256 для получения одноразовых ключей отправки и приёма (`tx_key`, `rx_key`) на базе **AES-256-GCM** (как уже используется в `anchor.py` и `keyvault.py`).
3. **Зависимости без раздувания ядра:**
   - В основном пакете `padam-nocturne` не требовать C-компиляции `liboqs` по умолчанию — сделать отдельную опциональную группу `pip install "padam-nocturne[pqc]"` (например, `cryptography>=48` или `xwing-kem` при наличии), а при попытке PQC-синка без библиотеки — честный отказ с инструкцией установки, без тихого отката на не-постквантовый режим.

## 3. Какие риски для защиты

1. **Самописный комбинатор X25519 + ML-KEM («свой XOR/конкатенация»):** ошибки при объединении секретов порождают атаки понижения версии. *Мера:* никогда не писать свой KEM-комбинатор — использовать только стандартный X-Wing (с включением обоих публичных ключей в SHA3-256) или проверенный HPKE-набор библиотеки `cryptography`.
2. **Уязвимость нулевого контакта (TOFU / MITM при первом спаривании):** постквантовый KEM не спасёт, если при первом знакомстве устройств злоумышленник подменил публичный ключ в незащищённом канале. *Мера:* обязательное ручное подтверждение 6-значного кода / QR-отпечатка (`SAS`) человеком при добавлении нового устройства.
3. **Несовпадение колёс (wheels) `liboqs` на Windows/macOS:** C-библиотека Open Quantum Safe часто не ставится без компилятора. *Мера:* предпочесть чистую Python/Rust-колесо реализацию `cryptography>=48` (если OpenSSL/BoringSSL в сборке поддерживает ML-KEM) либо протестировать prebuilt wheels под Windows/Linux/macOS до релиза.
4. **Конфликты `forget` (право на забвение) при асинхронной синхронизации:** если устройство A забыло запись и уничтожило ключ, а устройство B позже шлёт старую копию этой записи, она не должна «воскреснуть». *Мера:* синхронизировать в первую очередь `forget_receipt` / статус `revoked`, и отклонять восстановление любых ID, присутствующих в реестре уничтоженных ключей.
